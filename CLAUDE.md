# CLAUDE.md — working contract

Instructions for Claude Code in this repository. It is the only document that has to be read in
full. The roles are in `.claude/agents/`, the commands in `.claude/commands/`, the skills in
`.claude/skills/`, the checks in `gates/`.

## The idea

This idea arises from the complexity of carrying out a good data science project, with code that follows good practices and a valid result. 

A pipeline can run clean, pass every test and still produce a useless model because one column carried information from the future. Everything that follows exists so that a machine catches that difference.

## This is the multi-agent layer, not a project template

This system does not create `data/`, `src/`, `tests/` or any other directory of your project. The system adapts to those folders according to the project at hand, not the other way round. Three environment variables adjust where the gates look if you do not use the default conventions:

| Variable | Default | What it adjusts |
|---|---|---|
| `DS_SRC_DIRS` | `src,tests,experiments` | What `py_audit.py` audits |
| `DS_SRC_ROOT` | `src` | Where `mypy` runs |
| `DS_IMMUTABLE_DIRS` | `data/raw,wiki/raw` | What `git_audit.py` protects against writes |

What the system does create is its own output, because none of it existed before you used it:
`specs/` (each issue's executable shadow), `experiments/` (audits and evaluations),
`evals/` (golden sets and the ledger), `wiki/` (what gets learned). Those four are new content,
not pre-existing structure this system overwrites.

## What lives where

```
CLAUDE.md                The contract. This document.
setup-repo.py            One-time bootstrap: labels, branch protection on GitHub.
.claude/agents/*.md      The 6 roles — Claude Code subagents.
.claude/commands/*.md    The 5 human commands — slash commands.
.claude/skills/*/        Methodology that ds-manager invokes (define-tests/evals/metrics).
.claude/settings.json    The hook that actually enforces "red before green".
gates/                   Executable checks in plain Python — no dependency on Claude.
specs/, experiments/,
evals/, wiki/            What gets generated by using the system.
```

There is no `sync.py` and no generation layer. `.claude/` is the source, written directly in its
final format — nothing to translate, nothing to regenerate when you change a role or a command.

## GitHub is mandatory, and there are three points, not two

All work starts at an issue and ends at a PR. Three points require a person:

| Point | Command | What you do |
|---|---|---|
| **Create** | `/create-issue` (or `/grill-me` if the idea is raw) | You approve the spec: criteria, tests/evals/metrics, scope |
| **Implement** | end of `/implement-issue` | You see the complete PR — diff, commits, evidence, wiki — locally and confirm before it touches GitHub |
| **Merge** | you review the PR on GitHub | You approve or request changes. Merging IS accepting the result |

`/implement-issue` runs without pausing until the local PR is assembled — data, implementation per
criterion, integration, **the only looks at the resources that may only be looked at once**, wiki
compilation. It does not ask permission halfway. But it does not touch GitHub until you confirm
the local PR.

## Six roles, two convergence loops

```
ds-manager       interrogates until it converges, writes the issue, methodology in review and fixes
analyst          the data gate: leakage, performance ceiling, split strategy
ds-developer     implements: red, then green, per criterion. Calls wiki-generator at the end
reviewer         code correctness, not methodology. Read-only
validator        runs test/eval/metric once everything has converged; leads the fix; the only one
                 who looks at any one-look resource
wiki-generator   compiles what was learned into the wiki, once per issue, when everything has
                 converged
```

Researching techniques (SOTA, what approach the literature uses for a kind of leakage) is not a
separate role: it is a tool `ds-manager` and `ds-developer` use directly.

```
grill-me:         explores the repo, asks one at a time with its own recommendation,
                  always runs inside create-issue after its light discovery
create-issue:     ds-manager writes → analyst (data gate, if there is a metric) → issue
implement-issue:  per criterion: ds-developer ↔ {reviewer, ds-manager}, converges
                  → validator runs the integration against dev, ↔ ds-developer if it fails, converges
                  → the only looks (one per resource: metric, eval golden set)
                  → ds-developer calls wiki-generator, compiles what was learned
                  → local PR → (your confirmation) → PR on GitHub
```

Two convergence loops, one round budget per criterion: `gates/convergence.py` counts the rounds of
the per-criterion review and those of `validator`'s fix conversation on the same counter — a fix
that moves from one loop to the other does not reset the cap (3 rounds by default).

| Phase | Role | Happens in |
|---|---|---|
| Light discovery, then deep interrogation with exploration | `ds-manager` (via `/create-issue` → `/grill-me`) | Creation |
| Spec and test/eval/metric classification | `ds-manager` (via `/create-issue`) | Creation |
| Data audit, performance ceiling | `analyst` | Both (when needed) |
| Red, then green, per criterion | `ds-developer` ↔ {`reviewer`, `ds-manager`} | Implementation, converges (cap 3 rounds) |
| Integration against dev; fixes if it fails | `validator` ↔ `ds-developer` (+ `reviewer`/`ds-manager` if it touches code) | Implementation, converges (same cap, same counter) |
| Looks at one-look resources | `validator` via `gates/holdout_ledger.py`, one call per resource | Once each |
| Compile the wiki | `wiki-generator`, called by `ds-developer` | Once, at the end |

Two ways back. **DATA → SPEC**: if the data ceiling is below a criterion, `/create-issue` fixes
the target before creating the issue, or `/implement-issue` catches it if the data changed
afterwards and **stops and comments on the issue**. **Either convergence loop on itself**: past
the `gates/convergence.py` cap, it stops and reports.

## TDD, EDD and Metrics

Every acceptance criterion is verified in one of three ways, according to **the nature of the
verdict**:

| | Verdict | Example |
|---|---|---|
| **test** | Binary, repeatable | "rejects a row with no identifier" |
| **eval** | Binary, over an LLM output | "the answer cites a retrieved document" |
| **metric** | A distribution with a threshold and a CI | "AUC-PR ≥ 0.42, CI95 above the baseline" |

Rule: *same input, same output → test; otherwise → eval or metric.* A model metric is never an
`assert` in the suite: `gates/py_audit.py` fails it as `FRONT001`.

## Two classes of one-look resource

Not just the test partition of a model metric. The `dev`/`test` of an eval golden set follows the
same logic: looking at it repeatedly during a fix turns it, bit by bit, into a second validation
set. Both are recorded in the same `gates/holdout_ledger.py`, each under its own path — it counts
looks per file, so they do not share a budget, but each is looked at once.

## Hard rules

- **The directories in `DS_IMMUTABLE_DIRS` are immutable.** Derived data is regenerated by script.
- **Nothing is implemented without an approved spec.**
- **Red before green.** `gates/tdd_guard.py` checks it; the `red` commit comes before the `green`
  one and it goes in even though it fails.
- **Each one-look resource is looked at once per issue**, when `validator` has no fix conversation
  open, recorded in `gates/holdout_ledger.py`.
- **Every metric carries a confidence interval** (bootstrap, n≥1000) or it is not reported.
- **Seeds fixed and recorded.**
- **One change per iteration.**
- **Every reported metric records the commit hash** that produced it.
- **The wiki is compiled once per issue, at the end**, never in the middle of a fix loop.

## Data: DVC by default

Large files under `DS_IMMUTABLE_DIRS` (typically `data/raw/`) are versioned with DVC, not git:
`dvc init` once, `dvc add data/raw` per source, `dvc remote add` for where the real data live (S3,
GCS, a shared disk — the choice is yours, this contract does not presume one). The pointer
(`data/raw.dvc`, small) goes to git; the data go to the remote.

`dvc install --use-pre-commit-tool` generates the `.pre-commit-config.yaml` hooks at the right
version — the block already there is a reference, do not hand-edit it if you can regenerate it.
This is orthogonal to `gates/holdout_ledger.py`: DVC versions the whole dataset, the ledger counts
looks at one resource inside one issue. Both hash, for different reasons.

## Git

One branch per issue: `<n>-<slug>`, with no leading slash — `gh issue develop` fails on some
versions when the name contains slashes. One commit per criterion, prefixed with the issue number:
`red(#n-ACx):`, `green(#n-ACx):`. The history demonstrates the discipline —
`gates/git_audit.py` checks it. Never `git add -A`.

**All work is local until Step 10 of `/implement-issue`.** `setup-repo.py` turns that into
something GitHub blocks technically: the default branch rejects direct pushes from anyone.

## Before showing any local PR

```
python3 gates/check.py
```

It is exactly what CI runs. `mypy` is optional: it is reported but does not block, by design — see
`gates/check.py` if you want to change that. A blocking check is never relaxed to turn it green.

## Code quality: Ruff

`ruff format` is compatible with Black's output; `ruff check` includes the Flake8-equivalent
rules and, with the `I` set, isort's. A single formatter with two modes (format +
check).

## WIKI: record of what has been learned

`README.md` describes the tool: how to install it, what commands exist. It changes rarely.
**Everything else goes to the wiki** — GitHub Wiki convention, no generation or build:
`wiki/raw/` (sources, immutable), `wiki/log.md`, and a fixed hierarchy of six pages plus
`Home.md` and `_Sidebar.md` (`templates/wiki/` carries the template for each one):

```
Home.md                                Front door, index of decisions and failures
_Sidebar.md                            Side navigation — must link to all six
1.-Configuration-and-Environment.md    Installation, dependencies, Docker
2.-Data-Lifecycle.md                   Sources, ETL, data dictionary
3.-Exploratory-Analysis.md             EDA findings, leaks investigated, notebooks
4.-Modeling-and-Experiments.md         Features, experiments, tracking
5.-Evaluation-and-Metrics.md           Result with CI, segmentation
6.-Production-and-Monitoring.md        Deployment, monitoring, drift
```

No new pages are created. `decisions/` and `failures/` have no page of their own: they are
recorded as subsections (`### 📌 Decision: ...`, `### ⚠️ Failure mode: ...`) inside the page of
the phase where they occurred, indexed from `Home.md` — that keeps the **why**, which is what
made those two folders valuable before, without leaving the fixed hierarchy. `gates/wiki_lint.py`
checks that none of the six is missing, that `_Sidebar.md` links to all of them, broken links and
unresolved contradictions.
