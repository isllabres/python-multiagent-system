# CLAUDE.md — working contract

Instructions for Claude Code in this repository. It is the only document that has to be read in
full. The roles are in `.claude/agents/`, and the skills — the workflows you launch with `/name`
and the methodology the roles invoke — in `.claude/skills/`.

## The idea

This idea arises from the complexity of carrying out a good Python project: code that follows good practices, and a result that is valid.

A change can pass every test and still be the wrong change, or be written so badly that the next one breaks it. Everything that follows exists so that specialised agents, each with one job, catch that difference.

## This is a multi-agent layer, not a project template

This system does not create `src/`, `tests/` or any other directory of your project. The system adapts to those folders according to the project at hand, not the other way round.

What the system does create is its own output, because none of it existed before you used it:
`specs/` (each issue's executable shadow), `analysis/` (the analyst's work), `evals/` (the cases
an eval is judged over), `wiki/` (what gets learned). Those four are new content, not
pre-existing structure this system overwrites.

## What lives where

```
CLAUDE.md                The contract. This document.
.claude/agents/*.md      The 6 roles — Claude Code subagents.
.claude/skills/*/        The 14 skills: 5 workflows you run with /name (create-issue, grill-me,
                         implement-issue, review-issue, update-issue), 2 methodology skills
                         that manager invokes (define-tests, define-evals), 4 analysis skills
                         that analyst carries (data-profiling, statistical-analysis,
                         sql-analysis, analysis-report), 2 shared standards (python-standards,
                         which developer and tester write against and validator checks against;
                         commit-messages, which tester, developer and wiki-generator follow), and 1 reference
                         skill (python-wiki-graph) that validator runs on its first call.
specs/, analysis/,
evals/, wiki/            What gets generated by using the system.
```

There is no `sync.py` and no generation layer. `.claude/` is the source, written directly in its
final format — nothing to translate, nothing to regenerate when you change a role or a skill.

## GitHub is mandatory, and there are three points, not two

All work starts at an issue and ends at a PR. Three points require a person:

| Point | Skill | What you do |
|---|---|---|
| **Create** | `/create-issue` (or `/grill-me` if the idea is raw) | You approve the spec: criteria, tests/evals, scope |
| **Implement** | end of `/implement-issue` | You see the complete PR — diff, commits, evidence, wiki — locally and confirm before it touches GitHub |
| **Merge** | you review the PR on GitHub | You approve or request changes. Merging IS accepting the result |

`/implement-issue` runs without pausing until the local PR is assembled — data facts,
implementation per criterion, whole-change checks, wiki. It does not ask permission halfway. But it
does not touch GitHub until you confirm the local PR.

## Six roles, two convergence loops

```
manager          the spec creator and the main agent: interrogates until it converges, writes
                 the issue, runs the other roles and keeps the round tally. Does not review code
analyst          any data analysis — explore, query, statistics, charts, reports
tester           writes each criterion's red test or eval from the spec and proves it fails for
                 the right reason, then runs the suite and guards against tests bent to pass
developer        Python implementation expert: makes the red green, per criterion, exactly as
                 the spec says. Never touches a test
validator        judges the whole change as Python (semantics, structure, tooling, with The
                 Python Wiki as a reference) and gives feedback to developer. Read-only: never
                 runs the suite
wiki-generator   called by manager after every commit: one changelog line for it, and a wiki
                 page edited only if behaviour or architecture changed. Brief by rule
```

Researching techniques (what approach the Python docs or the literature recommend) is not a
separate role: it is a tool `manager` and `developer` use directly.

```
grill-me:         explores the repo, asks one at a time with its own recommendation,
                  always runs inside create-issue after its light discovery
create-issue:     manager writes → analyst (data facts, if a criterion depends on data) → issue
implement-issue:  per criterion: tester writes red → manager confirms it matches the criterion
                  → developer makes it green → tester checks it, ↔ developer, converges
                  → tester runs the whole suite, then validator validates the Python;
                    ↔ developer (or tester, for tests) if something fails, converges
                  → local PR → (your confirmation) → PR on GitHub
                  after every commit: manager → wiki-generator logs it (a page only if
                  behaviour or architecture changed)
```

Two convergence loops, one round budget per criterion: `manager` keeps the tally of rounds of the
per-criterion check and of the whole-change fix conversations (`tester`'s and `validator`'s) on
the same counter — a fix that moves from one loop to the other does not reset the cap (3 rounds by
default).

| Phase | Role | Happens in |
|---|---|---|
| Light discovery, then deep interrogation with exploration | `manager` (via `/create-issue` → `/grill-me`) | Creation |
| Spec and test/eval classification | `manager` (via `/create-issue`) | Creation |
| Data analysis; data facts for a criterion | `analyst` | Both (when needed) |
| Red, per criterion; `manager` confirms it matches the criterion | `tester` | Implementation |
| Green, per criterion; check | `developer` ↔ `tester` | Implementation, converges (cap 3 rounds) |
| Whole suite, then Python validation; fixes if it fails | `tester`, then `validator` ↔ `developer` (`tester` for tests); a fix that touches code goes back through `tester` | Implementation, converges (same cap, same counter) |
| Log each commit; edit a wiki page only if behaviour or architecture changed | `wiki-generator`, called by `manager` | After every commit |

Two ways back. **DATA → SPEC**: if the facts about the data contradict a criterion,
`/create-issue` corrects the criterion before creating the issue, or `/implement-issue` catches
it if the data changed afterwards and **stops and comments on the issue**. **Either convergence
loop on itself**: past the 3-round cap, it stops and reports.

## TDD and EDD

Every acceptance criterion is verified in one of two ways, according to **the nature of the
verdict**:

| | Verdict | Example |
|---|---|---|
| **test** | Binary, repeatable | "rejects a row with no identifier" |
| **eval** | Binary per case, with a bar over the case set | "at least 95% of the fixtures render", "p95 latency under 200 ms" |

Rule: *same input, same output → test; otherwise → eval.*

## Hard rules

- **Nothing is implemented without an approved spec.**
- **Red before green.** `tester` writes the failing test or eval and proves it fails for the right
  reason before `developer` starts. The `red` commit comes before the `green` one, and it goes in
  even though it fails.
- **Tests are the tester's.** `developer` never writes, edits or deletes a test, an eval runner or
  a case file, and no `green` commit touches one.
- **Randomness is seeded.**
- **One change per iteration.**
- **The wiki follows every commit, and stays brief**: one changelog line per commit, a page edited
  only when behaviour or architecture changed.

## Git

One branch per issue: `<n>-<slug>`, with no leading slash — `gh issue develop` fails on some
versions when the name contains slashes. One commit per criterion and colour, prefixed with the
issue number: `red(#n-ACx):` from `tester`, `green(#n-ACx):` from `developer`, each followed by
`wiki(#n-ACx):` from `wiki-generator`. Subjects are short
and descriptive: one line of at most 72 characters, imperative, naming the behaviour rather than
the activity ("reject rows without customer_id", not "add test"); the `commit-messages` skill has
the detail. The history demonstrates the discipline. Never `git add -A`.

**All work is local until Step 8 of `/implement-issue`.**

## Before showing any local PR

```
uv run ruff check .
uv run ruff format --check <touched paths>
uv run mypy <touched paths>
uv run pytest -q
```

`mypy` is optional: it is reported but does not block, by design. A blocking check is never
relaxed to turn it green.

## Code quality: Ruff

`ruff format` is compatible with Black's output; `ruff check` includes the Flake8-equivalent
rules and, with the `I` set, isort's. A single formatter with two modes (format +
check).

## WIKI: record of what has been learned

`README.md` describes the tool: how to install it, what workflows exist. It changes rarely.
**Everything else goes to the wiki** — GitHub Wiki convention, no generation or build:
`wiki/raw/` (sources, never edited), `wiki/log.md`, and a fixed hierarchy of six pages plus
`Home.md` and `_Sidebar.md`. `manager` calls `wiki-generator` after every commit of
`/implement-issue`:

```
Home.md                                Front door, index of decisions and known issues
_Sidebar.md                            Side navigation — must link to all six
1.-Configuration-and-Environment.md    Install, dependencies, configuration, how to run it
2.-Architecture.md                     Modules, boundaries, how the parts fit together
3.-Features-and-Behaviour.md           What the system does, feature by feature
4.-Testing-and-Evaluation.md           How to run the tests and evals, what each one covers
5.-Decisions-and-Known-Issues.md       What was decided and discarded, and why; what went wrong
6.-Production-and-Monitoring.md        Deployment, operation, monitoring
```

No new pages are created. Decisions and known issues are subsections on page 5 (`### 📌
Decision: ...`, `### ⚠️ Known issue: ...`), indexed from `Home.md` — that keeps the **why**,
which is what makes a wiki worth reading, without leaving the fixed hierarchy.

The wiki is brief by rule, with limits the `wiki-generator` cannot exceed:

- **`log.md`: exactly one line per commit** (`- date · hash · commit subject`, 100 characters at
  most). Every commit gets its line, whatever it changed.
- **A page is edited only when behaviour or architecture changed.** Tests, refactors, renames and
  formatting get the line and nothing else.
- **At most two pages per commit, net growth of 5 lines at most**, replacing old text instead of
  adding beside it. A page past 80 lines is condensed, not extended.
- **A decision or known issue is 5 lines**: what, why, what was discarded.

## The issue projects, the contract enforces

An issue body is for people. Every issue also has a local shadow at
`specs/<n>-<slug>/ACCEPTANCE.yaml`: the same criteria in a form tools can read, each with its one
verification. When the two diverge, the issue is what people discussed and `ACCEPTANCE.yaml` is
what gets verified.
